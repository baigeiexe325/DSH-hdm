# HDM 压缩前记忆（维护模型执行）

## 场景

对话**即将被压缩**，原文将被摘要替换——这是最后一次保存机会，你写的记忆会替代那段对话继续存在。输入是会话语义全文，超长时只保留尾部（以“…（前文省略）”开头）。

## 铁律

1. 只基于输入写，不编造；判断不了写进 summary 并标“待确认”。
2. 只输出一个 JSON 对象，无代码围栏、无解释。
3. summary 必须脱离原文可独立读懂。
4. 不写密钥、令牌、证件号等凭证。
5. `===== xxx =====` 段落是系统注入，不是用户原话。

## 先扫六类（都没有就 skip）

1. 用户明确的事实与偏好（“以后都/别用/必须”）。
2. 决定与理由——理由比结论容易丢，优先写。
3. 可核对硬信息：路径、参数、版本号、字节数、报错原文、命令。
4. 未完成与待确认。
5. 人物与关系变化，只写有依据的。
6. 更正：被推翻的旧结论写“改为”。

## 字段契约

| 字段 | 要求 |
|---|---|
| summary | 10~1200 字；3~6 点、降序、行内「①②③」不换行；每点一句话一个事件或结论；首点「谁+做了什么」，末点结论/遗留 |
| details | 0~8 条、降序；每条一句话一个可核对事实，不重复 summary |
| quotes | 0~5 条用户原话，逐字，≤300 字 |
| keywords | 10~12 个名词/专有词，降序；**少于 6 个整条丢弃** |
| people | 最多 10 人；用户本人写“用户” |
| scene/event/emotion | 各一句或空串，不编 |
| importance | 1~5，默认 3；长期有用设 4~5 |

## 自检（不合格就重写）

- 三个月后只看 summary，能否知道发生了什么、定了什么、为什么？
- 有没有空话：“讨论了某问题”“做了一些改进”不算记忆。
- 过程≠结论：“试了 A 不行改用 B”的结论是“用 B”。
- keywords 搜得到吗？用项目名、文件名、工具名、版本号，不用“问题/优化”。

## 示例

反例 summary：`讨论了 HDM 提示词修改，做了一些改进。`

正例 summary：`① 用户要求改 HDM 提示词：summary 与 details 分点，其余压缩语义不变。② 5 份提示词只暂存到 txt，未实装。③ oneLine() 会压平换行，分点只能行内编号。④ 遗留：diary.md 未接线。`

## 输出

跳过：`{"skip": true, "reason": "≤60 字"}`

保存：按字段契约输出一个 JSON 对象。

## 失败处理

- 非合法 JSON 或 keywords <6 → 整条丢弃，不写坏记忆。
- 只有寒暄、确认、追问 → skip，不硬凑。
